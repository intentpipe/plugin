# Design

Why the intentpipe looks the way it does. Grounded in Anthropic docs/engineering posts and 2025-26 practitioner evidence (sources at bottom).

## Core thesis

The intuitive design is an org chart of specialist agents (supervisor, frontend/backend engineers, designer, test engineer, reviewer, meta-agents). The evidence says the working part of autonomous coding is not the org chart — it is a **verify-gated loop over small tasks with fresh context and file-based state**. Multi-agent parallelism wins on independent *read* work (research, review); it loses on interdependent *write* work like coding (Anthropic: ~15x tokens, "most coding tasks involve fewer truly parallelizable tasks"; Cognition: conflicting implicit decisions).

So the spine is:

```
updates/ → /plan → tasks/NNNN-slug/ → per task:
  fresh implementer (TDD) → verify.sh (deterministic gate) →
  fresh reviewer (≤2 rounds) → squash-merge (one commit/repo;
  DONE=pr: push branch + pre-reviewed PR instead) →
  digest to tasks/_log.md → next task
escalation at every step → NEEDS_HUMAN.md + notify
```

Everything mechanical is a script; LLMs are invoked only where judgment is required (decompose, implement, review, arbitrate). Fewer calls, less drift.

## Where the specialist roles landed

| Role | Became | Why |
|---|---|---|
| Supervisor | Main session running `/build` + `scripts/task.sh` | Orchestration is mostly mechanical → code. Judgment (decompose, arbitrate) stays in the main loop with minimal context. |
| Backend Engineer | `implementer` agent | One implementer per task **spanning all repos** — a split frontend/backend pair drifts on the API contract (Cognition's core failure mode). |
| Frontend Engineer | `implementer` agent | Same. Cross-repo task still yields one commit per repo via squash-merge. |
| Frontend Designer | `/design` skill | A standing concept agent produces unverifiable prose. As a skill it runs on demand for UI-heavy tasks, output lands in the task folder where the implementer uses it. |
| Test Engineer | Implementer's TDD contract + `verify.sh` | Writing tests ≠ running them. Red-before-green is in the implementer prompt; execution is a deterministic gate, not an agent. |
| Reviewer | `reviewer` agent | The one specialist that clearly earns its context: fresh-context critique beats self-review. Findings are severity-typed; only `blocking` re-loops; hard cap 2 rounds. |
| Agentic Resources | `/retro` skill | Meta-improvement is kept, but **human-gated**: it writes proposals + diffs, never edits live prompts. Unsupervised prompt self-editing measurably degrades pipelines (slop accumulation, goal drift). A hook physically blocks writes into the plugin dir. |
| Tool Engineer | `/toolsmith` skill | YAGNI as a standing agent. Invoked when a repetitive need is *observed*, it wraps it as a project script/skill. |

## Decisions (with the socratic objection that shaped each)

1. **Task folders named `NNNN-slug`, not commit names.** *Objection:* the commit hash doesn't exist until after the work — chicken-and-egg. Folder id is stable pre-commit; the resulting SHA is written into task.md and a `Task-Id: NNNN` trailer goes in the commit message. Bidirectional link, no paradox.
2. **One commit per feature = presentation, not unit of work.** *Objection:* a single end-of-feature commit kills the incremental red/green signal that makes loops converge. So: implementer commits freely on `task/NNNN-slug`, verify runs per change, and `task.sh done` squash-merges to exactly one commit per repo. One-commit rule satisfied, verification cadence preserved.
3. **tasks/ is the single source of truth.** No separate TODO list to drift. Status lives in each task.md; `task.sh next/status` read it; `tasks/_log.md` is an append-only one-line digest per finished task (bounded supervisor memory). Crash-resume falls out for free: all state transitions hit disk before proceeding.
4. **Deterministic verification is the engine.** `verify.sh` (per-repo build/lint/test from agents.env) gates every step. Hierarchy of trust: compiler/tests >> fresh-context critic >> LLM-as-judge. Implementer is forbidden from weakening tests to pass — and the reviewer checks for it.
5. **Review converges by construction.** Findings typed `[blocking|nit]`; nits are logged, not re-looped; max 2 rounds; still blocking → `task.sh block` escalates to human. Never an unbounded ping-pong.
6. **Escalation is a first-class outcome.** Stuck detection (blocked result, failed verify loop, round cap, budget cap) → status `blocked`, entry in NEEDS_HUMAN.md, `notify.sh`. An autonomous system without a designed exit thrashes.
7. **agents.env is generic and preflighted.** Named repos (`REPOS="frontend backend"`), not a hardcoded frontend/backend topology — works for CLI tools, libraries, monorepos. `preflight.sh` validates it (repos exist, trees clean, verify green) before any agent runs; config is verified, not assumed.
8. **Distribution = Claude Code plugin, per-project state = files in the workspace.** Cloning the intentpipe into each project forks and drifts; submodules are friction. A plugin installs once, is enabled per project, propagates via `/plugin update`, and is consumed read-only. Project-specific bits (agents.env, updates/, tasks/) live in the workspace.
9. **Self-improvement = self-*proposing*.** `/retro` mines review.md + human feedback.md for recurring failures and writes `proposals/` entries with evidence and a concrete diff against this repo. Human reviews and commits. Prompt changes are release-engineered like code.
10. **Human comms: files first.** NEEDS_HUMAN.md + notify.sh (stub: macOS notification; add a Telegram/ntfy curl when async mobile approval is proven to be the bottleneck — don't build the messaging layer before the loop is validated).
11. **Two drive modes, same contracts.** Interactive: you run `/plan` then `/build` in a session. Headless: `scripts/loop.sh` runs `claude -p "/build <id>"` per task with iteration/cost caps — fresh context per task (the ralph insight) with deterministic task selection.
12. **Budgets are hard stops.** loop.sh caps tasks per run and cost per run (parses `total_cost_usd`); per-task cost is recorded in task.md so /retro sees spend, not just outcome. *Exception:* on a Claude subscription there is no per-token bill, so `total_cost_usd` is an API-equivalent estimate, not real spend — loop.sh detects subscription mode (no `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`, not Bedrock/Vertex), skips the cost cap, and records `Cost: subscription`. The task cap stays the only hard stop there. **Cost is always reported in tokens too** (`usage` from the same envelope, cache reads included, rounded to `xxk`): the dollar figure is an estimate on a subscription, the token count is what was actually spent — so `Cost: subscription (~$0.42 API-equiv, 1852k tok)`.
13. **Intent iteration = drop a note in `updates/`, plan the delta.** There is no living spec document. Human intent enters as free-form notes in `intentpipe/updates/`; /plan commits them verbatim (git history is the durable record — no spec_2 files, no accumulated document to drift) and turns them into tasks, then removes the notes it planned. Each task.md records the note commit it was planned from (`Intent:` field) and code commits carry `Task-Id` — so /retro can trace rework to its spawning note and separate misunderstanding (pipeline signal) from a changed request (product evolution, not actionable). The human's contract with the pipeline is the **approved task plan**, not a spec. See #26 for why the earlier living-spec model was retired.
14. **Usage limits pause the loop; they don't block tasks.** *Objection:* loop.sh treated every nonzero `claude -p` exit as a task failure, so a subscription limit cascaded — each remaining task got blocked and NEEDS_HUMAN.md filled with non-problems. A limit is an environment condition, not a task outcome: `limit_wait` (lib.sh) recognizes the limit message, sleeps until the advertised reset (fallback `LIMIT_BACKOFF`, default 30 min), and loop.sh retries the *same* task. Interrupted WIP is parked as a commit on the task branch (squash-merge erases it later) so preflight stays green, and `task.sh start` resumes an in-progress task by checking out its existing branch. Only genuine failures still escalate. **14b — the pause is bounded and announced once.** *Objection:* waiting was unlimited and notified on every attempt, so one task polled a limit for 3.5 hours and sent seven identical Telegram pings — the loop looked alive while making no progress, and the pings trained the human to ignore the channel. Waiting is right for a limit that clears; a limit that hasn't cleared after `MAX_LIMIT_RETRIES` (default 6) *consecutive* waits is not that kind, so loop.sh stops with exit 5 and says how long it waited. The counter resets whenever a task finishes — a limit that cleared is proof the waiting worked, so only unproductive waits count. Notification budget is two: the first wait (which explains a stalled loop) and giving up; the ones between say nothing new and stay in the log.
15. **A session that ends in-progress is finished, not blocked.** *Objection:* the merge (`task.sh done`) runs inside the one-shot `claude -p` session; when that session ends a step early the work is committed on the branch but never merged, and loop.sh's old safety net just marked it `blocked` and moved on — a half-finished task escalated as a failure. The merge is not the model's to lose. So loop.sh drives an in-progress result to a terminal state: first deterministically (review approved + branch has commits → run `task.sh done` from bash, no extra model call; `verify.sh` inside it still gates a red tree), else by re-invoking the same task up to `MAX_RESUME` (default 3) — `task.sh start` resumes the existing branch so build continues into review + merge — and only then blocking. Consistent with #14: a truncated session is an interruption to retry, not a task outcome. Leftover WIP is parked as a commit first (same as #14) so the resume's preflight stays green.
16. **Repos and intentpipe state are siblings under the project root.** State lives in `intentpipe/` (agents.env, updates/, tasks/, NEEDS_HUMAN.md); code repos are top-level dirs referenced as `../<repo>`; the root keeps only CLAUDE.md + .claude/. `find_workspace` probes `intentpipe/agents.env` too, so scripts work from the root, the state dir, or inside a repo. Flat layouts (agents.env at the root) keep working.
17. **Team mode is one knob, not a fork: `DONE=local|pr`.** *Objection:* why not auto-detect an origin remote? A solo project may push for backup; guessing would silently change merge semantics. Explicit in agents.env, validated by preflight (origin present, `gh` authenticated). Everything upstream of the terminal state — plan, implementer, verify, reviewer — is mode-blind, so mode 1 users see zero change.
18. **`DONE=pr`: the platform is the merge arbiter.** In a shared repo, local squash-merge bypasses team review and races a moving upstream. So `task.sh done` pushes the task branch and opens a PR carrying the task contract plus the agent review (the PR arrives pre-reviewed); "one commit per feature" (#2) is delegated to the repo's squash-merge policy. The task parks at `Status: pr`; deterministic `task.sh sync` (run by preflight) reconciles against GitHub — merged → done + digest + branch cleanup, closed-unmerged → blocked. tasks/ stays the single source of truth (#3) by reconciliation instead of monopoly. Fresh base: pr-mode preflight fetches and `--ff-only`s the default branch whenever a repo sits on it, so every task branches from current upstream. Known limit: a task that builds on a still-unmerged PR would branch without that work — /build stops and says so (stacked PRs are deliberately not built).
19. **A red upstream parks the loop; it doesn't block tasks.** Same shape as #14: a teammate breaking `origin/DEFAULT_BRANCH` is an environment condition, not a task outcome. When pr-mode preflight's verify fails with every repo sitting exactly at `origin/DEFAULT_BRANCH`, it exits 3 (`UPSTREAM RED`) and loop.sh notifies + retries after `UPSTREAM_BACKOFF` (default 30 min) instead of filling NEEDS_HUMAN.md with someone else's breakage.
20. **A blocked task gates its successors; an env crash retries, then hard-stops.** *Objection:* loop.sh treated every nonzero `claude` exit as the task's fault and marched on — a blocked task left its repo on the task branch, so every dependent failed preflight before doing any work, and the loop respun them with only an opaque `WARN`. Three fixes, each at the right layer. (a) The block-gate lives in `task.sh next`, not loop.sh, so it holds for the headless loop and interactive `/build` alike: `next` halts (exit 3) at a blocked task, running only todos *before* it; `CONTINUE_ON_BLOCK=1` overrides for independent sets. (b) A crash that never started the task (status still `todo` — no network, a stranded tree) is an environment condition, not a task outcome: retry the same task up to `MAX_RETRIES` (default 10) with `RETRY_BACKOFF` between tries and *without* spending the task budget, then hard-stop with the captured reason and leave the task `todo` for a clean re-run. Distinct from `MAX_RESUME`, which drives an *in-progress* task to finish. (c) The failure reason is captured once (claude's JSON envelope, else the last stderr line — where connection errors land) and surfaced to both the human (`loop-fail.log` + the `task.sh block` reason → NEEDS_HUMAN + notify) and the retry (threaded into the resume prompt). Consistent with #14/#19: environment conditions pause or stop the loop; they don't blame the task. *Not yet done:* `task.sh block` still leaves repos on the task branch (the `next` gate prevents the cascade, but a human must restore the branch before unrelated work).
21. **A cold-start orphan resumes or restarts; it never releases a dependent.** *Objection:* the resume path in #15 reads the in-iteration `status` var, so it only finishes a task that went in-progress *during this run*. A session killed mid-task leaves an orphan in-progress that a *fresh* loop never sees — `task.sh next` returned only todos and silently skipped in-progress, and its dependency gate held for `blocked` deps but not in-progress ones (treated as "in flight, will land"). So a killed run flipped 0037 → in-progress, and the next run's `next` skipped it and released 0038 (`Depends on 0037`) onto a prerequisite that didn't exist, in a repo stranded on the empty 0037 branch. Fix at one layer: `task.sh next` now returns the first *actionable* task — todo **or** in-progress — in id order. Returning in-progress does double duty: it self-heals the orphan (loop.sh builds it, `task.sh start` resumes its branch) *and* gates its dependents (a prerequisite counts as satisfied only when done/pr, so an unfinished one sorts first and holds the queue) — no separate resume loop, and it protects interactive `/build` too. loop.sh reconciles once at cold start: an orphan with committed work is left for `next` to resume; a *zero-commit* branch (killed before any work) is `task.sh abandon`ed — repos restored to `DEFAULT_BRANCH`, empty branch deleted, back to todo — so it restarts clean instead of resuming an empty branch. `task.sh reopen` folds in the same rule (empty branch → abandon, not the old "keeps in-progress because a branch exists"), and `task.sh abandon` is the explicit clean-restart verb that replaces the by-hand branch deletion this used to need; it uses `git branch -d` so committed work is never silently discarded. Consistent with #15: an interruption is retried or restarted, never blamed on the task. *Still not done (as #20):* `task.sh block` leaves its repo on the task branch — deliberate, since blocked WIP is committed and a human inspects it there, and the `next` gate already stops the cascade.
22. **Green, committed work is finished, never blocked for a missing review verdict.** *Objection:* the in-progress backstop (#15) merged deterministically only when `review.md` said `VERDICT: approve` — but a resume that lands on an already-complete, already-green branch can end without ever running review, so no verdict is written, the net can't fire, and three no-op resumes then `task.sh block` a task whose acceptance tests all pass. That is the opposite of what the gate is for. Fixed at the source *and* the backstop: (a) the build skill always spawns the reviewer and writes a verdict, even on a resume where implementation is a no-op — removing the missing-artifact case; (b) loop.sh's deterministic finish no longer *requires* an approve verdict — it merges when the branch has commits and either the review approved, the resume **stalled** (rc=0 + no new commit, detected by fingerprinting branch tips via `branch_head` — another resume would just no-op), or the resume budget is nearly spent. `task.sh done` still runs `verify.sh`, so a red tree is never merged; the only thing bypassed is an LLM review the session failed to produce, and blocking green, tested work is the worse outcome. (c) When it must block, the reason carries the verify color (GREEN/RED) so a human can tell finished-but-unmerged from genuinely broken. Hierarchy of trust (#4) is preserved: the compiler/tests still gate; only the fresh-context critic is skipped, and only as a last resort.
23. **A transient API/network drop is retried, never resume-counted, never fatal.** *Objection:* loop.sh classified only usage-limit (wait for reset) and out-of-credits (exit 4); a dropped connection ("connection closed mid-response") fell through to the generic path. Because `/build` runs `task.sh start` early, the drop landed with the task already **in-progress** (often zero-commit), so the in-progress backstop treated a network blip as "session made progress, resume it" — counting it against `MAX_RESUME` — and under `set -e` a stray nonzero in the resume iteration could terminate the entire headless run on one blip. The one failure class that is purely external and self-clearing was the one loop.sh didn't survive. Fix: `is_transient_api_error` (lib.sh) recognizes self-clearing drops (reading claude's JSON `result` field in preference to raw stderr, so a task whose own output says "internal server error" isn't misread as a drop); loop.sh handles it *before* the generic path and regardless of status — a zero-commit branch is `abandon`ed (un-stranded, clean restart), committed work is parked — then retries the SAME task on the `MAX_RETRIES`/`RETRY_BACKOFF` budget (the env-crash path, **not** `MAX_RESUME`), hard-stopping only on a persistent outage. Defense in depth (#20b): the env-retry guard also catches a nonzero exit that left an in-progress zero-commit branch, and the in-progress backstop only fires when there is committed work to resume. Consistent with #14/#19: external conditions pause or restart the loop; they never blame the task or kill the run.

24. **Human comms grew an outbound Telegram leg (proposal 2026-07-09).** #10 deferred the messaging layer until the loop was validated; it now is (23 decisions, v0.10.0). `notify.sh` sends a `sendMessage` when `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` are set — shared creds in `~/.agent-orchestrator/telegram.env`, per-project `TELEGRAM_TOPIC_ID` in agents.env — so a project's escalations land in its own forum topic. Tolerant by construction (#10's "files first" still holds): notify never fails its caller — no creds, no workspace, or a dead network → it prints and moves on, as before. Telegram, not WhatsApp (only Telegram's Bot API creates the "community + one topic per project" model programmatically). notify.sh is the *seam*, nothing more: the inbound side (a daemon that routes messages back into `updates/`, per-project topic creation, any server-wide tooling) is inherently cross-project — above any single workspace — so it lives in a **separate** server-side project the plugin knows nothing about. The only contract between them is the filesystem: shared creds in `~/.agent-orchestrator/telegram.env`, notes dropped into a workspace's `updates/`. The plugin depends on neither.

25. **Features group tasks into PRs: task = commit, feature = PR (`DONE=pr`).** *Objection:* one PR per task floods a team repo with micro-PRs — tasks split a feature into loop-sized units, so the task is the right *commit* granularity but the wrong *review* granularity. So /plan groups tasks into features at plan time (`Feature:` in task.md, membership in `tasks/_features/<slug>.md`) — grouping is decomposition judgment, so it lives in /plan and the human approves the PR boundaries with the plan. Mechanics recurse #2 one level up: `task.sh done` squash-merges the task onto `feature/<slug>` (the existing local-merge path, retargeted via `task_base` in lib.sh — which also keeps `branch_has_commits`, and with it loop.sh's orphan/resume machinery, correct for feature tasks), and when the feature's last member task is done, `ship_feature` pushes the branch and opens one PR carrying every task contract + review. Bonus: member tasks branch *from* the feature branch, so intra-feature dependencies see each other's work — #18's stacked-PR limit now applies only across features. A task is `done` when it lands on its integration target; the feature file owns upstream state (`open → pr → done|blocked`), reconciled by the same `task.sh sync` (closed-unmerged → feature blocked + NEEDS_HUMAN; which tasks to reopen is human judgment). `Feature: -` keeps the per-task PR; `DONE=local` ignores features entirely — everything lands on the default branch anyway.

26. **The living spec was retired; intent notes are the only input surface (retro 2026-07-16, `proposals/2026-07-16-retire-living-spec.md`).** *Objection:* isn't the spec the human's contract with the pipeline (original #13)? In practice the living `specs/*.md` document earned nothing a mature project could keep precise: (a) it never drove tasks — the delta in `specs/updates/` did, while the accumulated document was a coverage ledger /plan half-distrusted ("check the repos before tasking specced behavior"); (b) in an existing codebase the code is the source of truth, so a maintained prose copy only drifts; (c) it was a second source of truth for *intent* — exactly the drift #3 forbids for *status*. Its one unique consumer, /retro's misunderstanding-vs-changed-request discriminator, reads *more* directly from the note that spawned the rework ("actually make it X" = correction; "now also do Y" = evolution). So `specs/` and its `updates/` subfolder collapse to one flat `intentpipe/updates/` of consumed notes; /plan drops the absorb-into-spec step and the spec-diff approval (the human approves the task plan); `Spec:` becomes `Intent:`. Named `updates/`, not `specs/`, precisely so the folder name stops re-summoning the document model — the one cosmetic cost is calling a greenfield project's first note an "update", which the steady state (updates all the way down) outweighs. Deliberately kept out: a single human-readable "what is this system" doc — a *product* concern, and a drifting one is worse than none; keep a README if you want one, the pipeline doesn't depend on it. Onboarding becomes uniform (greenfield drops one big note; a mature repo drops its first change), which removes the init-time spec-gap friction rather than patching it.

27. **The scaffold owns its own topic's inbound; only the transport stays server-side.** *Objection:* #24 said the plugin knows *nothing* about inbound — but "inbound" is two jobs, and only one is cross-project. (a) *Transport/demux* — holding the bot's `getUpdates` stream and splitting updates by `message_thread_id` — must be a single, always-on, server-side consumer: a shared bot's getUpdates is single-consumer (parallel workspace pollers would steal each other's updates), and the plugin has no persistent process to hold the poll. (b) *Per-topic handling* — turning this project's messages into its `updates/` intent notes — carries no cross-project knowledge and is the plugin's to own, symmetric with notify.sh owning the outbound leg of the same topic. So the seam moves down one level: the server (the one persistent consumer, holding only a topic→workspace-path table) demuxes and drops each *raw* message into `<workspace>/updates/.inbox/`; `inbound.sh` (mirror of notify.sh, run first by /plan) moves each into an `updates/tg-<epoch>-<msgid>.md` note. Note naming and format are the plugin's business — the server never learns `updates/` conventions, staying a generic Telegram→filesystem pipe. Tolerant like notify.sh (no inbox, no workspace → no-op); messages queue until the next /plan drains them, which is fine because intent is only consumed at plan time. Unchanged from #24: the always-on consumer, forum-topic creation, and new-project routing stay in the separate server project — genuinely cross-project. What #24 over-claimed, and this corrects, is only the note-handling for a topic already bound to a workspace.

28. **Linear tracking is opt-in and rides the feature slug, not `task.sh` (proposal 2026-07-19-linear-issue-per-plan).** *Objection:* "use the issue's branch name for the git branch" collides with #25 — a plan run makes *several* `feature/<slug>` branches (the only pushed ones; per-task `task/<id>-<slug>` branches are local plumbing, squash-merged away), but Linear suggests one branch name per issue. Resolved by leaning on Linear's case-insensitive *containment* match: /plan creates **one** issue per approved plan run (`scripts/linear.sh create` → `issueCreate` GraphQL, prints `<KEY>\t<url>`) and prefixes every feature slug with the key lowercased (`feature/eng-123-<slug>`), so every PR from the run auto-attaches to the one issue with **zero change to `task.sh`** — the key is just part of the slug `cmd_new` already slugifies. Gated on `LINEAR_TEAM_KEY` (agents.env, per-project) *and* `DONE=pr` (linking is via the pushed PR branch; meaningless under `DONE=local`); `LINEAR_API_KEY` is shared in `~/.agent-orchestrator/linear.env`, mirroring the telegram creds split (#24). When on, the skill wraps even a one-off task in a feature so its branch carries the key (a featureless task pushes `task/<id>-<slug>`, which wouldn't). Mechanics/judgment split holds: the GraphQL call is `linear.sh`; the issue title, checklist, and key-prefixed slugs are /plan's. One-directional like the note→intent dependency — plan → issue → PRs; no status sync back, no sub-issue per task (deliberately out of scope: a drifting mirror of task state is worse than none, echoing #3/#26).

29. **Base freshening happens once, at plan kickoff — not per-build (amends #18).** *Objection:* #18 fast-forwarded the default branch in preflight, before every build, "so tasks branch from current upstream." But under `DONE=pr` the default branch only advances when a human merges a PR, and a build run spans many tasks: re-freshening mid-run yanks a repo onto a moved base *while an earlier PR from the same run is still open*, and a later feature then branches from a base that has drifted out from under the plan. The human's objection was concrete: "when the target is PR I don't want the system to jumping back to dev before I actually merged the PR." So the base is set once, at the natural fresh-start line — `/plan` kickoff runs `freshen.sh`, which fetches `origin/DEFAULT_BRANCH` and moves every *clean* repo onto it (a repo with uncommitted changes is reported and left as-is; a dangling task branch is left intact, never deleted). Preflight drops the ff *advance* but keeps the `fetch` its upstream-red check (#19) and `task.sh sync` (#18) compare against — so the base is now a fixed point for the whole run, and no repo is pulled onto a moving default branch between opening a PR and its merge. The trade #18 made (always-latest base → fewer conflicts at PR time) is deliberately reversed for a stable base (predictable, never clobbers an open PR); the cost — a later feature not seeing an earlier same-run PR's merged work — was already #18/#25's documented stacked-PR limit, now simply fixed at plan time instead of drifting per-build. *Deliberately deferred:* a resumed task branch that has gone stale against a since-moved base is **not** locally rebased — mechanical salvage of stale work is the wrong tool and the conflict case is rare; the intended resolution is to **replan** the task against current `dev` (re-decomposition is higher-value than a fragile rebase, and stays human-gated through `/plan`). Detecting staleness → routing to replan is a follow-up, not built here.

30. **An open PR accepts amendments; merge closes the window automatically (extends #25).** *Objection:* PR review feedback ("on this PR, also do X") had no pipeline entrance — /plan only built new work from fresh base, so acting on feedback meant hand-editing the branch. Resolved at the feature layer, where the PR already lives: a note amending a still-open PR is planned as new member tasks of that same feature (`task.sh new` with the existing slug — no new plumbing; `task_base` already branches them from the live `feature/<slug>`, and `ship_feature`'s reuse path pushes their commits onto the existing PR). The window closes at the mechanics layer, not by prompt discipline: `task.sh new` refuses a feature whose Status is `done`/`blocked`; /plan runs `task.sh sync` at kickoff so a merge flips Status before planning; and sync blocks any amend task a merge raced past (feature merged upstream while the task was unfinished → its integration branch is gone → blocked with a replan reason, same one-way door as #18's closed-unmerged). Featureless task PRs are deliberately not amendable — amending a lone task branch has no reviewable integration point; plan a follow-up (under Linear, #28 wraps everything in features anyway). Hardened in the same change: /plan consumes note *files* only — the guard now blocks `rm` of `updates/` itself and wildcarding its contents, so the folder and its README survive every plan run (the folder's persistence was always implied by #26; now it is enforced).

31. **`/unblock` diagnoses a stuck queue and auto-resolves only the safe cases.** *Objection:* escalation is already first-class (#6) — why a command to un-escalate? Because a block is a mixed bag: some are genuine judgment calls a human must make, but others are purely mechanical (the merge step never ran on green, tested work — #15/#22's failure mode when it slips past the loop's own backstop; or a session died before landing anything, leaving a task to retry). The mechanical ones don't need a human, just the right deterministic verb — and hunting through NEEDS_HUMAN.md, `loop-fail.log`, and `review.md` to tell which is which is the toil the command removes. Split holds (#4's mechanics/judgment line): `task.sh diagnose` is the deterministic data-gather — one global verify color plus, per stuck item, has-commits / review verdict / faillog / the NEEDS_HUMAN reason; the `/unblock` skill supplies the judgment. It auto-resolves exactly two safe classes — **finished-but-unmerged** (`commits=yes` + verify GREEN → `reopen` then `done`, the same deterministic merge loop.sh runs, `done`'s own verify still the gate) and **nothing-built** (`commits=no` → `reopen` resets to `todo` for a clean retry, un-stranding the repo) — and *escalates the rest* with a precise reason (RED-with-commits, review non-convergence, a real implementer question, a blocked feature, a closed PR). Deliberately conservative: it never edits code, never forces a merge, never bypasses a red verify — a wrong auto-fix is worse than an honest escalation, so anything needing code judgment stays a human's call. Reachable headless via the daemon's `unblock` trigger (🩹), symmetric with 🧠/plan and 🚀/build; a failed *plan* run (notes present, no tasks) is diagnosed as "re-run /plan", not acted on here. *Not built:* auto-rebuilding RED/review-blocked tasks (bounded-resume auto-repair) — a plausible next tier, left off until the safe pass is trusted.
32. **A task's unmade product decision is asked, not guessed (`Decision:` gate).** *Objection:* the builder can already `task.sh block` when stuck — why a dedicated gate? Because the worst case wasn't a clean block: a task whose Goal buried an unmade product call ("flowers wilt over 7 days" — a proposal, not a spec) let the headless builder either invent the answer or, correctly refusing to, end with no committed work — which the loop read as a zero-commit orphan and *reset to todo*, respinning the same task every run (queue frozen, budget bled, no human ever asked). The decision was neither made nor surfaced. Fix, split across the mechanics/judgment line (#4) and the two comms legs (#24/#27): /plan sets a `Decision: <question>` field on any task that hinges on a call the human hasn't made (judgment — the planner recognizes the gap); loop.sh detects the field before building, blocks the task (so `next` gates the queue, #20), and posts the exact question into the topic via `ask.sh` with "Reply to this message to decide" — remembering `message_id → task` in the server's run dir. The daemon (the one persistent inbound consumer, #27) routes a *reply* to that message to `task.sh resolve`, which folds the answer into the task as a `## Decision (resolved)` note the builder reads, clears the gate, and reopens it to `todo`. Deterministic verbs (`ask.sh`, `task.sh resolve`) carry the mechanics; the question and the answer are the human's. Consistent with #6: a genuine decision is a first-class escalation, but one that asks a precise, answerable question and folds the reply straight back in — not a NEEDS_HUMAN line a human must hunt down and hand-resolve. `notify.sh` grew a `NOTIFY_SILENT` knob so the block and the question don't double-post.

33. **Verify proves the app runs, not just that it compiles: optional `SMOKE_<repo>`.** *Objection:* the gate already runs each repo's build+lint+test — what does booting add? A whole failure class it structurally cannot see. Incident: a merged migration narrowed a CHECK without deleting the rows violating it; every gate builds its database from scratch (fresh CI service container; a test DB holding only what the seed plants), and the same commit deleted the seed code that produced those rows — so after it, no gate could *generate* the data that breaks the migration. A removal task is untestable against a from-scratch database, and the first execution of the shipped startup path was a human opening the preview to a dead API. Same shape for a bad env var, an import error at module scope, a broken seed. So: `SMOKE_<repo>` in agents.env, one command proving the artifact starts and answers, run after `VERIFY_<repo>` passes (a repo failing its own tests has nothing to smoke). **Optional** — repos without it are unchanged, which is most of them (libraries, config repos). **Explicit, never auto-detected** — the plugin cannot know which service is the app, which endpoint proves readiness, or whether the project uses containers at all; same reasoning as #17 (`DONE` is a declared knob, not a sniffed origin remote) and #43 (agents.env is a generic repo list, not a hardcoded topology), and a wrong guess either hangs the gate or greenlights a dying app. **`timeout ${SMOKE_TIMEOUT:-300}` owns the process** — a container that never turns healthy must fail the gate, not wedge the loop. The honest cost: verify stops being side-effect-free (smoke *starts things*, and a meaningful command forces a real boot rather than no-op'ing on an already-running container), and the implementer's inner loop pays the boot time — hence `--no-smoke`, used by the two callers that only want a status color (`task.sh diagnose`, documented read-only; `loop.sh`'s block-reason color) and available to the implementer between changes. The two real gates — `preflight.sh` and `task.sh done` — always run it. Scope follows the unit being gated (retro 2026-07-29): `preflight.sh` sweeps every repo once per run (workspace health), the implementer's loop verifies only the task's declared `Repos:`, and `task.sh done` runs those repos in full while the rest go tests-only (`--no-smoke`) — a cross-repo test break must not land green, but a smoke command with side effects (`--force-recreate` on a live preview) must not fire for a repo the task never touched.

34. **A finished task reports where its time went, measured by the scripts themselves.** *Objection:* the loop already reports cost and outcome — isn't wall-clock just vanity? No: "that took 40 minutes" is unactionable, while "34m of it was `flutter test`" and "18m was the model, 3m the gates" point at different fixes (a slow suite vs. an over-long session), and until it is measured the loop's most expensive step is a guess. The measurement must not depend on the LLM cooperating — a step the model forgets to bracket silently disappears — so **each deterministic step times itself**: `preflight.sh` and `verify.sh` append `<step>\t<seconds>` rows to `tasks/<id>/timings.tsv` (`verify:<repo>`, `smoke:<repo>` — per repo, so a slow suite is named), and loop.sh adds the one step no script can see, `llm` = session wall clock **minus whatever the scripts recorded while it ran**. That subtraction is what keeps the rows non-overlapping, so their plain sum is the task's real total and no step is double-counted (verify runs twice — inside the build, again in `task.sh done` — and correctly shows as twice the time). `INTENTPIPE_TIMING_ID` (exported by loop.sh around the session) pins nested scripts to the right task even as its Status changes. The summary lands in `task.md` (`Timing:`) next to `Cost:`, so /retro sees duration profile alongside spend, and the raw rows stay in the task folder for anything finer.

## Steelman we accepted

"Why not a single agent loop and nothing else?" — Mostly right, and this design *is* that loop at its core. The only standing specialists are the implementer (fresh context per task) and the reviewer (generate/critique separation — cheap, well-evidenced). Everything else was demoted to skills or scripts. Roles get added back only when a specific context demonstrably doesn't fit — earn the agent.

## Deliberately not built (yet)

- Multi-user intentpipe state (several plugin users on one project): push the workspace repo to a shared remote; claiming = `Owner:` field + optimistic git push (rejected push = lost race, pull and pick another task); a `Needs: <id>` field gates `task.sh next`; `merge=union` for the append-only _log.md/NEEDS_HUMAN.md. `DONE=pr` already handles code integration between users. Build when a second plugin user exists.
- Parallel implementers in worktrees (agent teams): worktrees solve file collisions, not decision conflicts. Add when tasks are provably disjoint and the sequential loop is trusted.
- Telegram bridge: `notify.sh` (out) + `inbound.sh` (in) are the plugin's seams (#24, #27); the always-on server-side consumer that feeds them is external by design.
- LLM-as-judge quality gates: weakest verifier class; deterministic gates + reviewer cover it.
- Token-level budget accounting inside interactive sessions (CLI exposes cost only in headless JSON output).

35. **Verify owns its test runners' process group and reaps what they leave behind.** *Objection:* a leaked worker is the test runner's bug — why absorb it here? Because it stays unfixed while the loop pays for it: `flutter test` left a `flutter_tester` behind on *every* run, and systemd counted eight distinct survivors spanning days ("Unit process 81653 (flutter_tester) remains running after unit stopped"), 8h 20min of CPU, a 6.2G memory peak and 1.8G swap peak on a 4G box — so each build competed with its predecessors' corpses, and the slowest step (#34) got slower for no reason. The loop cannot patch someone else's runner, but it can refuse to leak: `verify.sh` runs each `VERIFY_<repo>` and `SMOKE_<repo>` command through `run_reaped`, which puts it in its own process group and, once it returns, sends the group TERM then KILL after a grace. `set -m` (not `setsid`) creates the group, so the pgid is exactly `$!` — guaranteed by bash, no external binary and no racy `ps` lookup, which returned an empty pgid often enough to leak in testing. Exit codes are untouched (`timeout`'s 124 still reaches the smoke branch), and the Ctrl-C that now stops at the script — the run being in another group — is forwarded to it, so an interrupted gate leaks nothing either.

36. **What a landed task triggers is a declared command, not a built-in: optional `AFTER_DONE`.** *Objection:* `task.sh done` ends by putting every repo back on `DEFAULT_BRANCH` (#17's PR path) — deliberately, so the next task branches from a clean base. But anything *serving* the project keeps serving whatever is checked out, so the moment a task landed the preview reverted to the mainline: a human amending a PR from the phone got a rebuilt preview of `dev`, not of the branch just built, and the only way back was to hand-pick the branch again in the server's checkout flow. The gap is real, but the fix is not the plugin's to hardcode — it has no idea whether a project *has* a preview, a deploy, or nothing at all, and #24 is explicit that the server-side consumer is external and the plugin depends on neither. So the plugin ships the seam and nothing else: `AFTER_DONE` in agents.env, one command run when a task lands, with the branch that now carries the work as its argument — the PR branch, the feature branch it integrated into, or `DEFAULT_BRANCH` under `DONE=local`. Explicit and never auto-detected, same knob discipline as `DONE` (#17) and `SMOKE_<repo>` (#33). **Detached and tolerant**, the shape `notify.sh` already established (#24): a real hook takes minutes (a preview is docker plus a release web build) and the loop must move on to the next task, and a side channel that fails must not fail the task — output lands in `tasks/_after-done.log`. Fired only when something actually landed (a no-change task moved nothing to follow) and only from `task.sh done`, not from `sync`: a merge is the *human's* state change, and rebuilding on it would fire during every `/plan` kickoff. **Deferred inside a loop run** (`INTENTPIPE_LOOP`, exported by loop.sh): the next task starts the instant one lands, so a hook that checks branches out would fight it — `done` records the branch and `finish_notify` fires the last one when the run is over, one hook per run instead of one per task, on a settled tree. The receiving end owes the same care in reverse: this server's refresh gives way to any repo sitting on a branch it didn't park there, so a hook that fires late can never yank a builder off its task branch. On this server the command is the orchestrator's `checkout.py --refresh`, which re-checks-out that branch across the repos that have it (repos without it stay on the default — the one-sided FE/BE rule) and relaunches with the database reset; that whole policy lives on the server side, where it belongs.

37. **An image is intent too — photos become permanent `resources/`, notes reference them, tasks carry them.** *Objection:* notes are text and Telegram photos could just be described in a caption — why a file pipeline? Because the picture *is* the spec in exactly the cases where words fail: a UI mockup, a screenshot of a rendering defect, a whiteboard sketch. The bibbles project grew a `intentpipe/resources/` folder by hand for precisely this (style specs, character sheets, tasks referencing them by path), proving the shape before the plugin adopted it. The seam split follows #27: the server-side consumer stays a dumb pipe — it downloads the photo next to its caption note in `updates/.inbox/`, referencing it by bare basename (`[image: <name>]`); `inbound.sh` (the plugin's leg) moves the image to `resources/tg-<name>` and rewrites the reference to the path a session actually reads. Resources are deliberately **not** notes: a note is consumed by /plan and deleted (git history keeps it), but the tasks planned from an image still need the file at build and review time — so resources persist, `snapshot_ws` commits them with the workspace state, and task.md carries a `Resources:` field so implementer, reviewer, and /design all look at the same picture instead of each interpreting the plan's prose about it. Hand-dropped files in `resources/` referenced from a note ride the identical path — Telegram is one producer, not the contract.

38. **Within-task retries resume the session; fresh context stays per-task (amends #14/#15/#23).** *Objection:* fresh context per task is the core insight (#11) — why carry anything over? Because the three retry paths were paying for a principle they don't serve. Measured across 136 headless build sessions: 94% of input tokens are cache reads (effective cost ≈ 0.17× the raw count — the per-task "1.2M tokens" headline is mostly cheap prefix re-reads), and each session writes ~35–135k of *new* content into context, the bulk of it orientation reading. A retry of the same task (usage-limit wait #14, transient drop with committed work #23, in-progress resume #15) restarted that orientation from zero: the new session re-read everything its dead predecessor had read, and could silently contradict its implicit decisions — the interruption was environmental, the conversation was fine, discarding it was pure cost. loop.sh now captures the envelope's `session_id` and re-invokes with `--resume`, so a retry continues the same conversation (files read, plan, partial work). Fresh-start paths still get clean context: a new task and an abandoned zero-commit branch reset the id. Bounds are untouched (`MAX_RESUME`/`MAX_RETRIES`/`MAX_LIMIT_RETRIES`) — resume changes what a retry costs, not how many happen. `--resume` forks to a new session id, so each attempt re-captures; output that yields no id keeps the previous one (resuming the last known session still beats starting over).

39. **Orientation is a subagent's job; memory banks the map (same measurement as #38).** The other lever on that ~35–135k of new content per session: cache-read volume grows as requests × context size, so a file read into the implementer's own context is re-paid by every turn after it — the expensive sessions (3–7M cache-read tokens) are the long-context ones, not the many-turn ones. Two prompt-level changes. (a) The implementer explores through a read-only `Explore` agent and acts on its conclusions, reading in full only files it will edit or the task names — conclusions enter the main context, file dumps don't. (b) Its `memory: project` store was accumulating only gotchas (test-font widths, alembic id collisions) and no layout; the prompt now directs it to also record the *map* — module layout, which file owns a behavior, project commands — so orientation that cost a search once is a lookup afterwards. Complements each repo's CLAUDE.md: that is the human-curated map, memory is the agent-earned one.

40. **One plan run = one feature = one PR per touched repo (amends #25).** *Objection:* #25 made feature grouping a decomposition judgment — "one feature = one coherent, reviewable PR" — precisely so PRs stay reviewable-sized. But measured against a real project (quorum, retro 2026-08-04-one-feature-per-plan-run), fine-grained grouping turned one intent note into nine features whose dependency chain (design system → feature view → chat pane) made every feature boundary a merge gate: the queue stalled three times on #18's documented stacked-PR stop, each stall waiting on a human merge before the next feature could branch from a base carrying the work it consumes. The human's resolution was explicit: "everything I collect should be turned into ONE PR by the planner" — fewer merge gates beat smaller diffs when merges come from a phone. So /plan now groups all of a run's tasks into a single feature; intra-run dependencies become intra-feature (member tasks branch from the feature branch — #25's machinery, unchanged), and #18's stop remains only for cross-*run* dependencies, where /plan's sync+freshen kickoff already makes the wait loud. The amendment flow (#30) is untouched, and a multi-feature split survives only as an explicit human request at plan time. Cost accepted with the decision: the PR opens at the run's end (previews still follow each landed task via #36) and one blocked task holds the run's PR. Prerequisite shipped alongside: `ship_feature` caps the PR body (contracts + reviews ≈ 82 KB for 8 tasks already exceeded GitHub's 65536-char `createPullRequest` limit, dying *after* the branch push — retro 2026-08-01-feature-pr-body-limit); the body now degrades stepwise — drop reviews, then truncate contracts, each with a visible footer — since the full contracts and reviews live on the branch regardless.

41. **The planner prices each task's build model; the run knob became an override (amends the MODEL pin).** *Objection:* `MODEL=opus` existed precisely so a session never silently runs on a cheaper model — doesn't per-task choice reopen that hole? No, because nothing here is silent: the model is a *planned* property of the task, chosen where the pipeline's judgment already lives — /plan sizes, splits, and gates tasks, and the same read of a task's difficulty prices it. A rename or copy change doesn't need opus-class reasoning, and cost concentrates in build sessions (#38), so a uniform opus run overpays exactly on the tasks that need it least. task.md carries `Model: sonnet|opus`, shown in the plan the human approves; loop.sh resolves it per task, defaults to opus when unset (older tasks and cautious plans are unchanged), and warns + falls back on an unknown value rather than dying mid-queue. The pick's asymmetry is stated in /plan: a wrong `sonnet` costs review rounds, a wrong `opus` only tokens — so unsure means opus. An explicitly set `MODEL=` still pins the whole run: the escape hatch for usage limits and credit stops (#14) must stay a one-knob override a human can apply from a phone without editing task files.

42. **`DONE=local` publishes: the merge is only half a terminal state.** *Objection:* #17 made mode explicit precisely so an origin remote wouldn't silently change merge semantics — doesn't auto-pushing reintroduce the guess? No: this changes where a *local* merge ends up, not who arbitrates it. Under `DONE=local`, `task.sh done` squash-merged into `DEFAULT_BRANCH` and stopped, so a green task existed only on the box — bibbles ran three tasks deep (0133-0135) with `origin/main` stale, found only because a human went looking, and a machine whose disk is the sole copy of a week's work is one crash from losing it. So `done` now calls `scripts/publish.sh`, which pushes `DEFAULT_BRANCH` for the repos the task touched. Per task, not per loop run: a run killed mid-flight (the usage-limit stop of #14 is the common case) still leaves origin current for everything that did land. Tolerant on the notify.sh/state-land.sh seam contract — every skip (no origin, nothing ahead, `DONE=pr`) is a printed reason and exit 0, and a *failed* push escalates via notify.sh yet still exits 0, because a publish problem must never fail a task that already merged green. Never force, never auto-merge: a rejected push means origin moved under us, and reconciling someone else's history is a human's call. `DONE=pr` is skipped outright — there the platform is the merge arbiter (#18) and hand-pushing the default branch bypasses review. The guard's ban on pushing the default branch is unchanged and still correct: it stops an *agent* from hand-pushing work that skipped the pipeline; publish.sh only pushes what `done` already verified and merged.

43. **Chatty output is context, and context is the bill (extends #38/#39).** *Objection:* #39 already moved orientation into a subagent — what is left to win? The other half of the same ledger: what *commands* print. Measured over 10 days of subagent transcripts (260 runs, ~$780 API-equivalent), 70% of the spend is cache reads and 5% is output — a session pays to re-send its context every turn, so cost tracks (context size × turns), not thinking. In the priciest single run ($27.53, 192 turns, 45.1M cache-read tokens) Bash results were 55% of all context growth: 142 calls averaging 1.4k tokens, mostly *green* test transcripts proving nothing the PASS line doesn't. Screenshots — the intuitive suspect — were 67% of that transcript's bytes but 8.6k tokens, because images are priced by dimension, not payload; they are not the problem and were left alone. Three changes, each at the layer that owns the waste: (a) `verify.sh`, the one command the implementer runs after every change (rule 4), prints the runner's summary line on green and a bounded, *named* log tail on red when its stdout is piped, staying fully verbose for a human at a terminal — mechanics in the script, per CLAUDE.md, not a plea in a prompt; (b) the implementer is told to ask commands for the verdict rather than the transcript, and to edit with Edit/Write instead of shell heredocs that echo the file back and spend a turn; (c) /plan prefers the smaller split, since cost grows faster than task size and one-feature-per-run (#40) already made splitting free of merge gates. Deliberately **not** done: a turn cap on the implementer. A task that genuinely needs 200 turns should get them — capping trades a real failure for a saving, and the size lever belongs at plan time where judgment already lives (#41). The measurement is now a tool rather than a one-off: `orchestrator/system-scripts/tokens.py` (Telegram `💰`/`tokens`) reprices the transcripts on demand, so the next claim about spend is checked, not remembered.

44. **Agent spawns in the build skill are synchronous — a headless turn-end kills background children.** The CLI's Agent tool runs subagents in the background by default and re-invokes the caller via a task-notification when they finish. That contract holds interactively but not under `claude -p`: when the orchestrating session ends its final turn, the run tears down and the notification arrives as `status: killed` — quorum 0034 lost 10 minutes of implementer work this way (spawned 12:37:59, killed mid-edit 12:47:59, uncommitted changes stranded, loop.sh blocked the task as "ended in-progress with no committed work"). Quorum 0033's repair agent hit the same teardown and survived only because its session happened to keep going. Mechanics can't own this one — the spawn happens inside the model session, out of scripts' reach — so the skill line pinning `run_in_background: false` is load-bearing: the orchestrator must hold its turn open until each agent returns. If a future CLI makes headless runs await background children, the line can go.

45. **The guard's default-branch ban is scoped to `DONE=pr` (amends #42).** *Objection:* the ban was a flat safety rail — doesn't making it conditional reopen the hole it plugged? Only where the hole was never real. The rail exists because under `DONE=pr` the platform is the merge arbiter (#18): an agent hand-pushing the default branch there lands work that skipped review, and no amount of prompt text reliably stops that, so it belongs in mechanics. Under `DONE=local` there is no arbiter to bypass — the pipeline itself pushes that branch on every landed task (`publish.sh`, #42), and the flat ban only ever blocked a human or agent from doing by hand what the machinery does automatically a minute later, while `state-land.sh` and `publish.sh` (running *inside* a Bash call, invisible to a PreToolUse hook that only sees the outer command) were never covered by it anyway. So `PR_MODE_DENY` is applied only when the workspace's `agents.env` says `DONE=pr`; `hooks/guard.py` resolves the mode by walking up from the session cwd exactly as `lib.sh`'s `find_workspace` does, and falls back to lib.sh's own default (`local`) when no workspace is found — a plugin dev session, or a stray directory. Fail-open is deliberate and small: the mode is read from a file the pipeline itself writes, and a guard that blocked every push it could not classify would break the plugin's own repo. The implementer's standing instruction ("never touch the default branch; never push") is unchanged in both modes — the guard is the backstop for that rule under `DONE=pr`, not its only statement.

46. **Sonnet builds by default, opus reviews regardless, and CLAUDE.md is read-only for the pipeline (extends #43).** Measured on quorum over 14 days ($248 API-equivalent, 4081 requests): 68% cache reads, 24% cache writes, 8% output — the bill is context × turns, and 41 of 48 tasks ran the implementer on opus at 2.5× sonnet's per-token price. Three changes. (a) /plan picks `sonnet` for every single-repo task and must write a `## Change map` (files, functions, tests) into task.md — the detail that lets a cheaper model land it; `opus` only for cross-repo work, an open design question or an unclear root cause, and a change map over ~6 files or two repos means split. (b) The reviewer agent pins `model: opus` instead of inheriting the session's model: a cheap implementer behind a strong reviewer is the right asymmetry, a cheap reviewer is how bugs ship. (c) Implementers were growing project `CLAUDE.md` files into module maps (quorum-core's reached 13.7 KB, one paragraph naming every module, re-paid on every turn of every session that touched the repo) because a rule said "bank the map" and nothing said where. There is no map: memory holds gotchas only (a capped one-line index), an `Explore` agent rebuilds orientation from the code when a task needs it, and `CLAUDE.md` keeps only what code cannot say. Mechanics, not a plea: `hooks/guard.py` refuses any Write/Edit of a `CLAUDE.md` and any Bash redirect or `sed -i` into one (`INTENTPIPE_ALLOW_CLAUDE_MD=1` for a deliberate human edit). Same ledger, smaller item: `_after-done.log` was an append-only 230 KB file committed and re-diffed by every state landing; `after_done` now keeps the last 200 lines.
