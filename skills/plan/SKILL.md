---
name: plan
description: Decompose the intent notes in intentpipe/updates/ into small, verifiable tasks. Run after dropping a note (or a batch).
disable-model-invocation: true
argument-hint: "[which note or area to plan, default: all unplanned]"
---

Turn the notes in `intentpipe/updates/` into tasks. Focus: $ARGUMENTS

Headless mode — when $ARGUMENTS contains `headless` (Telegram-triggered, nobody at a terminal): never prompt; anything a step below would say or ask goes through `${CLAUDE_PLUGIN_ROOT}/scripts/notify.sh` instead.

1. Freshen the base so tasks branch from current upstream: run `${CLAUDE_PLUGIN_ROOT}/scripts/freshen.sh` (no-op unless `DONE=pr`) — it brings every clean repo onto the latest `DEFAULT_BRANCH`. Report anything it flags (a repo skipped for uncommitted changes stays as-is; headless: via notify.sh). Then run `${CLAUDE_PLUGIN_ROOT}/scripts/task.sh sync` (no-op unless `DONE=pr`) so merged PRs complete their tasks and features before you plan — a merged feature no longer accepts amendments. Then drain the topic inbox: run `${CLAUDE_PLUGIN_ROOT}/scripts/inbound.sh` so any messages texted into this project's Telegram topic land as notes in `updates/` before you plan (no-op if none). Then commit any uncommitted notes as-written — the user's words stay in git history, and that history *is* the record of intent (there is no living spec document to maintain). Ignore `README.md`. If there are no notes to plan, ask the user what to build and stop (headless: notify "plan: nothing queued — text intent first" and stop).
2. Read the notes, `intentpipe/tasks/_log.md`, and `${CLAUDE_PLUGIN_ROOT}/scripts/task.sh status` output. A note may reference an image (`[image: intentpipe/resources/…]` — a photo texted into the topic lands there, and a hand-dropped file in `resources/` referenced the same way works identically). Read the image file itself — you can see images — it IS the intent: a mockup to build, a screenshot of a defect to fix, a sketch to interpret; the caption alone is not the note. Also run `${CLAUDE_PLUGIN_ROOT}/scripts/task.sh nits` — the build never re-loops a nit (DESIGN #5), so this is the only place they are triaged: fold the ones that touch code a note in this run already changes into that task's criteria, and name the rest you are consciously leaving. Plan only what the notes ask for and is not already covered by a task — nor already present in the code: in a pre-existing codebase, check the repos before tasking described behavior.
3. Draft the task list. Each task MUST have:
   - a goal one implementer can finish and verify in a single green run,
   - testable acceptance criteria ("WHEN <condition> THE SYSTEM SHALL <behavior>"),
   - explicit non-goals ("don't touch X") — which exclude other *work*, never another instance of the defect the note reports,
   - for a task whose client writes to a server: a criterion for the failed write (what the user sees, what the UI reverts to) and one for what the client renders after a refetch — without both, the implementer ships a swallowed error and optimistic state that never reconciles,
   - the repos it spans (cross-repo only when the feature genuinely spans them),
   - a change map: the files, functions and tests the implementer will touch, as far as you can see it (spawn an `Explore` agent to see it — that is planning effort well spent). Write it as a `## Change map` section in task.md. A change map of more than ~6 files, or one that spans repos, says the task is too big: split it.
   - a build model: `sonnet` by default — every task confined to one repo whose change map you could write. `opus` only when the task spans repos, settles a design question the note left open, or chases an unclear root cause; say which in the task's Notes. The reviewer runs on opus regardless of this pick, so a weak implementation is caught by a strong review; a wrong `sonnet` pick costs one cheap review round, a wrong `opus` pick costs 2.5× on every turn of the build.
   Prefer the smaller split. A build session re-pays its whole accumulated context on every turn, so what a task costs grows faster than its size: two half-size tasks come in under one double-size task, and each one lands, reviews, and fails on its own. Split whenever a task carries two separable deliverables; keep them together only when neither half can be verified alone. Under one-feature-per-run a split is nearly free — same feature branch, same PR, no extra merge gate. Too big to verify in one run → split it, always. Vague note → ask the user now, not the implementer later.
   If `DONE=pr` in agents.env, group **all of this run's tasks into one feature** — one plan run = one feature = one PR per touched repo (slug: a short name for the run's intent). Tasks land as single commits on the shared `feature/<slug>` branch and the PR opens when the run's last task finishes, so dependencies between this run's tasks are always fine — a fine-grained split turns each boundary into a merge gate the queue stalls on (retro 2026-08-04-one-feature-per-plan-run). Exceptions: tasks amending a still-open PR join that existing feature (next paragraph), and split into separate features only when the user explicitly asks for separately mergeable PRs.
   A note that amends work sitting in a still-open PR (its file in `tasks/_features/` says `Status: pr`) → plan its tasks into that **same feature**: pass the existing slug to `task.sh new`. They branch from the live feature branch and the open PR picks up their commits when they land. If sync marked the feature `done`, the PR is merged and closed to amendments — `task.sh new` refuses the slug; plan a fresh task/feature against the new base instead (say so to the user). A featureless task's PR cannot be amended; plan a follow-up.
4. Order by dependency, then present the list (with its feature grouping and each task's model pick; flag any task that amends a feature's open PR with that PR's URL from the feature file — the human must see what an amendment will land on, especially for transcribed voice notes) to the user for approval — the approved plan is the human's contract with the pipeline (headless: skip the prompt and proceed; approval is the 🚀 message that starts the build, sent after the human reads the list you post in step 5). Decomposition quality is the leading indicator of pipeline success — spend your effort here.
5. On approval, if `LINEAR_TEAM_KEY` is set in agents.env **and** `DONE=pr` (Linear links via the pushed PR branch, so it is meaningless under `DONE=local`), first create one issue for this whole plan run: `${CLAUDE_PLUGIN_ROOT}/scripts/linear.sh create "<plan title>" "<the task list as a markdown checklist, grouped by feature>"` — it prints `<KEY>\t<url>`. Then prefix every feature slug with the key lowercased (`eng-123-<slug>`) so each PR's branch auto-links to the issue, and group **every** task into a feature (wrap a one-off in its own feature — a featureless task's branch never carries the key). Skip this whole step if the key is unset.
   For each task run `${CLAUDE_PLUGIN_ROOT}/scripts/task.sh new "<title>" ["<repos>"] ["<feature-slug>"]` (each records the note commit it was planned from as `Intent:`), fill Goal / Change map / Acceptance criteria / Non-goals in the created task.md, and set its `Model:` field to the pick from step 3 (`sonnet`|`opus`) — loop.sh runs the build session on it unless the human pinned `MODEL=`. A task planned from an image sets its `Resources:` field to the path(s) — the implementer, reviewer, and /design read the same picture; resource files persist after the note is deleted, so the reference stays valid. If a task hinges on a product decision the user has **not** made (a lifetime, a threshold, an either/or — including how far a reported defect's fix reaches, when the cause you diagnose is shared with a surface the note didn't name), set the task's `Decision: <the exact question>` field rather than guessing; flagging an interpretation in prose "for review" is not an escalation, since the reviewer reviews against the criteria you wrote from it — the build pauses that task, posts the question on Telegram (reply-to-decide), folds the answer in, and resumes; never bury such a choice as a silent assumption in the Goal. Then delete the individual note **files** you fully planned and commit the deletion — git history keeps them; `intentpipe/updates/` holds only unplanned intent. Never delete the `updates/` folder itself, its `README.md`, or `.inbox/` (the guard blocks folder-level and wildcard deletion). Do not implement anything. Headless: finish by posting the created task list (titles + feature grouping — amendments flagged with their open PR URL — and the Linear url if one was created) via notify.sh — that post is what the human approves with 🚀. Then run `${CLAUDE_PLUGIN_ROOT}/scripts/state-land.sh` — it pushes the plan's workspace-state commits as a PR and merges it when the diff is state-only (its exit never blocks you).
